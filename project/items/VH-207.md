# VH-207 — Focus passes to the file chooser when an unreadable file withdraws the step that holds it

## Intent

Pass 3 found that choosing an unreadable file after a readable one, with focus on a Video language radio, leaves focus on the page's body (V-46, rank 2, regressed; WCAG 2.4.3). Both read-failure paths, the failed reply (`src/main.ts`, `:1486`) and the exception (`:1500`), call `clearTrim('unreadable')` (`:1756`), which withdraws steps 2 to 5, and step 6 unless a result stands, with no `focusHeldBy` capture and no successor. VH-178 gave the blocking branch its hand-on (`:1590–1596`) and never reached these two paths; VH-191 moved Video language into step 3, so the omission now drops focus from a control people use. Choosing the file is itself part of the transition: it runs `clearTrim('reading')` (`:1432`), whose control lock disables the trim (`:1765`, `:2462–2469`), and re-renders a standing result (`renderResult`, `:1443–1444`), which replaces its Save. This item applies the existing `focusHeldBy` / `stepsWithdrawnBy` pattern at both moments, the choosing and the failed read, on both read-failure paths, and hands displaced focus to the file chooser. It adds no element and changes no other caller. It is behaviour in `main.ts` and the walker's variants, walked by keys before any CSS in this pass moves.

## Acceptance criteria

- **At the choosing.** Before `clearTrim('reading')` and the result's re-render, a capture notes focus on a control they disable or replace. Focus on a trim control the reading lock disables lands on the file input. Focus on a standing result's Save lands on the re-rendered Save, the same logical control. A readable replacement and a block keep their behaviour after that.
- **Both read-failure paths hand focus on.** Focus taken while the read is pending, or kept through it, is captured: the controls the setup steps take away are captured with `focusHeldBy(stepsWithdrawnBy({ setup: false, create: resultStanding }))` before `clearTrim` changes anything, since its `applyControlLock()` (`main.ts:1765`) runs before the steps are hidden (`:1767`); once, where both paths meet, or at each caller; the build says which and why. Focus held in a withdrawn step lands on the file input, the chooser the person just used. With focus on a Video language radio, a title-card field, a closing or output control, or step 6 when no result stands, an unreadable file leaves focus on the file input.
- **The guards kept.** Focus held outside the withdrawn steps stays where it is; focus is never taken from the feedback dialog, nor from where a person has gone to read (`src/ui/focus-hand-on.ts`). With a result standing, step 6 stays (`resultStanding`), so focus on its re-rendered Save stays. Every other caller of `focusHeldBy` keeps its behaviour, checked by reading each one and by the keyboard routes.
- **The variants, both timings.** Walker variants, declared in the scenarios, proved and kept for VH-203: (a) focus on a Video language radio when the unreadable file is chosen (S-149's read-failure branch); (b) focus on a trim control when it is chosen, which the reading lock disables; (c) focus put on a Video language radio while the read is pending; (d) the J4 case, a finished video standing, focus in step 3, an unreadable file chosen beside it: steps 2 to 5 withdrawn, step 6's card and Save kept, focus on the file input; (e) focus on that standing Save when the file is chosen, which lands on the re-rendered Save; (f) focus in the feedback dialog, and on a reader's place, which stay.
- **The exception path** (`:1495–1500`, `took-too-long`) reached by a named inspection-failure fault this item declares and proves in the walker's faults (`reviews/2026-10-25/design-pass-3/evidence/measurements/walker/faults.mjs`): F14 holds only `preflighted` replies and F11 drops messages only once processing starts, so neither reaches it. If it cannot be reached by the walker, the build says why and a unit test proves the path.
