# VH-26 — Mobile phone sources

Working detail for the open backlog item. Raised by the maintainer 2026-08-25:
staff may upload "a myriad of mobile phone formats". No phone footage is in the
corpus yet, so this is analysis of the code against known phone behaviour, not
measurement.

## Rotation — checked, and correct

Worth recording because it is the most likely place for a silent disaster and
because the UI already promises it: `source-panel.ts` tells the user
"Rotated N°. The output will be upright."

That promise is honest. The chain was traced end to end through Mediabunny
1.55.2:

1. `media-sink.js:1330` — the decoder wrapper reads `track.getRotation()` from
   file metadata.
2. `media-sink.js:962` — it stamps that rotation onto every decoded sample.
3. `sample.js:1110` — `transform()` computes
   `normalizeRotation(this.rotation + (options.rotate ?? 0))`, so the sample's
   own rotation is applied even though we pass no `rotate`.
4. `outputShapeFor` is fed `displayWidth`/`displayHeight`, which Mediabunny
   reports already rotation-corrected — so the encoder is configured portrait
   for a portrait source, and `fit: 'contain'` has nothing to letterbox.

A portrait iPhone video therefore comes out upright at portrait dimensions.

**The footgun**: `transform.rotate` ADDS to the file's rotation, it does not
replace it. Anyone setting it to "make the output upright" would double-rotate
every already-tagged file. It must stay unset.

## Colour and HDR — a real gap

`grep` for `colorSpace`, `transferCharacteristics`, `primaries`, `bt2020`,
`hdr` or `toneMap` across `src/` returns nothing. There is no colour handling
at all.

Every iPhone since the 12 records HDR by default — HLG or Dolby Vision, BT.2020
primaries, 10-bit. Recent Android flagships likewise. The pipeline decodes to a
`VideoSample`, draws it through a canvas in `transform()`, and encodes `avc`
with no profile requested, which will resolve to 8-bit SDR.

What happens in between is the browser's canvas conversion, and it is neither
specified by us nor tested. The plausible outcomes are a reasonable automatic
tone-map, a washed-out grey picture, or crushed highlights — and which one
depends on the browser. The file always plays, so nothing surfaces as an
error; it just looks wrong, which is the failure mode `AGENTS.md` calls the
worst available outcome.

## Other phone characteristics to expect

- **HEVC**, the iPhone default. Accepted by the container list, but WebCodecs
  HEVC decode is patchy by platform. `safeCanDecode` should catch it and refuse
  cleanly rather than fail mid-job — worth an explicit fixture.
- **Genuine VFR.** Phones drop frame rate in low light and with auto-FPS. This
  is the real VFR the conform path was built for, and the corpus still has
  none — Teams and PowerPoint both turned out to be CFR (VH-24).
- **High frame rate**: 120 and 240 fps slow-motion, sometimes with the slow-mo
  as a timing edit rather than a rate change.
- **Very large files** from 4K60 recording, against the no-fixed-cap decision.
- **Portrait aspect** reaching the branding compositor, which has only ever
  been fed 16:9 and 16:10. A 9:16 output with a 16:9 logo over it needs a
  stated behaviour, not whatever `contain` happens to do.

## Done when

Phone footage exists in `samples/` — at minimum one portrait HDR HEVC clip and
one VFR low-light clip — the colour path has a decided, tested behaviour rather
than an emergent one, and portrait branding composition is specified.
