# VH-44 — The closing transitions are wrong in Firefox

Measured 2026-08-25 under the VH-34 spike, in all three supported engines. The
question VH-34 asked is answered; what is left is the fix. The reasoning behind
the answer is in decision-log 2026-08-25 "VH-34 spike"; this file holds the
numbers a fix has to satisfy.

## What was measured, and against what

Ground truth came from ffmpeg decoding the onsets straight out of the WebM, so
no browser sat between the file and the figure. The frame at t=0.40 s is
uniform across all 1920x1080 pixels, so pixel choice does not matter:

| Onset | Stored RGBA | Un-premultiplied, for comparison |
| --- | --- | --- |
| `closing-onset-fade-white-1080p.webm` | `(73, 73, 73, 75)` | `(248, 248, 248, 75)` |
| `closing-onset-fade-blue-1080p.webm` | `(4, 10, 17, 75)` | `(14, 34, 58, 75)` |

Both are premultiplied — RGB never exceeds alpha. The browser figures below
were taken through `BrandingCompositor.compose()` over a **black** picture, so
the correct output IS the stored colour. Black is deliberate: it is the
maximum-error case, and it is what a real closing over dark footage shows.

## Every route out of a decoded frame, in every engine

| Route | Chrome 151 | Firefox 154 | Safari 26.5.2 |
| --- | --- | --- | --- |
| A. `sample.draw()` then `getImageData` — what `compose()` does | correct | **un-premultiplied** | correct |
| B. `new VideoFrame(canvas).copyTo(RGBA)` | **double-premultiplied** | correct | **BGRA** |
| C. `VideoSample.copyTo(RGBA)` — no canvas at all | correct | correct | **luma plane** |

Raw figures, white then blue:

| Route | Chrome | Firefox | Safari |
| --- | --- | --- | --- |
| A | `(75,75,75,75)` / `(7,14,20,75)` | `(17,17,17,69)` / `(18,40,66,69)` | `(75,75,75,75)` / `(7,10,17,75)` |
| B | `(20,20,20,75)` / `(3,3,7,75)` | `(74,74,74,69)` / `(5,11,18,69)` | `(75,75,75,75)` / `(17,10,7,75)` |
| C | `(75,75,75,75)` / `(7,14,20,75)` | `(74,74,74,69)` / `(5,11,18,69)` | `(80,80,80,80)` / `(25,25,25,25)` |

Three things the numbers say that prose would blur:

- **Firefox route A is arithmetic, not noise.** `5 x 255/69 = 18.5` matches
  `(18,40,66)` exactly on all three channels. White then overflows and **wraps**
  instead of clamping: `74 x 255/69 = 273`, reported as **17**. A white closing
  over dark picture therefore inverts to near-black rather than glowing.
- **Firefox also rescales the alpha plane**, 75 to 69, as if it were limited
  range. That is what pushes white over 255 in the first place, and it breaks
  the `RGB <= alpha` invariant the file guarantees — which is why an
  arithmetic correction cannot be trusted to undo route A.
- **Safari's two failures are one cause:** it ignores
  `VideoFrameCopyToOptions.format` silently. On a canvas-backed frame that
  surfaces as BGRA — `(17,10,7)` is `(4,10,17)` reversed — and on a decoded
  frame as the raw luma plane (`Y = 16 + 0.859 x 73 = 80`, and
  `16 + 0.183 x 4 + 0.614 x 10 + 0.062 x 17 = 24` for blue). **The white onset
  hides both.** Grey is symmetric, so a white-only test passes a byte order
  that is reversed. Any regression test here must use blue.

## What a fix has to do

No single route is portable, so the fix cannot be a swap. The recommended shape
is a **startup probe against a known branding frame** — decode one onset, run
the candidate routes, keep the one whose RGBA matches the table above, and
refuse `over-picture` and `over-freeze` loudly if none does. `capability.ts`
already answers "can this device do this job?" and this is the same question
about a narrower faculty.

Route C is the one to prefer when it works: it is correct in two engines and
touches no canvas. It has a real cost, though — it returns the brand at its own
resolution, and `compose()` currently gets its scaling free from
`brand.draw(ctx, fit…)`. Taking route C means the composite loop samples the
brand through the fit rectangle itself, which is not hard, and removes a
full-frame canvas allocation while it is there.

Rejected, with reasons, so they are not re-derived:

- **Correct Firefox's route A arithmetically.** The overflow wrap destroys the
  value, and it survives only because Firefox's alpha rescaling breaks the
  invariant such a correction would key off.
- **Re-tag the assets full-range.** Would remove the wrap and leave the
  un-premultiply — fixing the symptom that is easiest to see and keeping the
  error.
- **Detect the browser.** Engine sniffing dates badly; the file's own known
  pixels are a better oracle than a user-agent string, and cost one decode.

## Reproducing

```bash
npm run dev
node scripts/run-in-engines.mjs /spike-alpha.html
```

That prints the whole table above, all three engines, in one run — the figures
here came from it. Safari needs "Allow Remote Automation" ticked once; see
`DEV-INFRASTRUCTURE.md` → "Cross-engine verification". Do not run it while
`npm run check` is running.
