## Measured so far

A stage profile in Node over a synthetic 600 s stereo programme
(`speechLike`, 44.1 kHz, 1,024-frame blocks, gain +6 dB into the limiter).
The machine was at load 100–140 from other sessions' test runs, so trust the
ratios and not the absolutes:

| Stage | Cost per hour of audio |
| --- | ---: |
| `TruePeakLimiter` | 208–274 s |
| `Compressor` | 29–45 s |
| `TruePeakDetector` | 27–82 s (noisy) |
| `LoudnessAnalyser` | 19–20 s |
| `HighPassFilter` | 5–11 s |
| Pass A (analyser) | 38–81 s |
| Pass B (steps 2–4 + analyser) | 58–102 s |
| Pass B′ / C (whole chain + analyser) | 244–433 s |

**The limiter is about 85% of every whole-chain pass**, and a job runs it in
every B′ pass and again in pass C. It, not the analyser, is the target.

## Tried and refuted

The window shift is NOT the cost. A rewrite of the limiter that replaced the
13-sample shift with a mirrored ring buffer (each sample written at `pos` and
`pos + 13`), and the modulo wraps with comparisons, gave bit-identical output
on every signal and chunk size tried and ran at x0.96 — no gain. Reverted,
not committed.

So the time is in the arithmetic itself. The likely reason: the exact skip
(`windowMax * MAX_PHASE_GAIN <= ceiling`) almost never holds once the chain
has applied its gain, so the full 4 x 13 convolution runs on nearly every
sample of every channel. Take a CPU profile (`--cpu-prof`) before the next
design; candidates to test then are a tighter exact skip, and doing the
convolution once per frame where it is now done per channel.

The compressor's cost is a `log10` and a power per sample, which no exact
rewrite removes. Leave it unless the profile says otherwise.

## Method

- A profiler can live outside the repo: a vitest config whose `test.dir`
  points at a scratch folder, run with `--disable-console-intercept` (or
  vitest swallows `console.log`). Import repo modules by absolute path.
- Compare old against new by snapshotting the old file from `git show HEAD:`
  and running both over the same blocks, byte-comparing the output.
- Time on a settled machine, or interleave old and new runs, so that
  contention cannot fake a result in either direction.
