# VH-32 — Interface quality pass

Raised by the maintainer 2026-08-25 after using the deployed app: "not bad, but
we need to approach it from a high quality critical view to create an amazingly
smooth product."

This is a deliberate design pass, not a bug list. What follows is what a first
critical read of the working app surfaces; it is a starting point for that
pass, not its scope.

## What the screen does badly today

**The page accretes rather than progresses.** Choosing a file adds a details
table, branding options, a preset choice, a readiness panel, a button, a
progress bar, and then a result — all stacked, all still present. After the
video is made, "Create the video" still sits above "Save the video" with a full
progress bar between them, so the finished state looks like the working state
with more underneath. There is no sense of having moved through steps, and
nothing collapses once it is settled.

**It speaks in file formats, not outcomes.** The source table lists Picture,
Frame rate, Sound, Subtitles, Container — `852 × 480, H.264`, `30.3 fps`,
`Stereo, AAC, 44.1 kHz`. A lecturer does not need to parse a codec name to know
whether their video is fine. "Measured speed — 282 frames per second on this
device" is worse: it is a number with no decision attached to it.

**The estimate is not trusted, correctly.** It said 27.7 MB and produced
7.5 MB (VH-31). A number that wrong is worse than no number.

**Disabled controls do not read as disabled.** The Animation group greys its
labels when the mode is a hard cut, but the radios themselves still look live.
The explanation sits below the group, after the controls it explains.

**Nothing shows what the branding looks like.** Fade versus Slide, Blue versus
White, and three ways the logo can arrive — all chosen blind, from text. This
is a *video* tool; the one thing it never shows is moving picture.

**Ordering follows the code, not the task.** Branding options come before "What
is this video for", though the destination is the bigger decision and the one
that changes the output most.

## Worth holding onto

The plain-language framing is already right in places and should survive the
pass: "Length — 2 minutes 10 seconds", "Best quality — for EchoVideo or
YouTube", "Your video is read on this device. It is never uploaded". The
reassurance about not uploading is doing real work and should stay prominent.

## Constraints the pass must respect

- `UI-STANDARDS.md`: WCAG 2.2 AA minimum, AAA where achievable; 44 × 44 pointer
  targets; Carbon tokens; both token systems kept distinct.
- The app must stay usable with no file chosen, mid-job, and after failure —
  three states that currently get little attention next to the happy path.
- Everything must work offline after first load (spec §11), so no web fonts or
  remote assets.
- A preview means decoding branding on the client, which is affordable (the
  onsets are 7–22 KB) but is real work, not a CSS change.

## Done when

A considered redesign is agreed and implemented, not a list of tweaks applied.
Worth a design review against `UI-STANDARDS.md` §6 before it is called done.
