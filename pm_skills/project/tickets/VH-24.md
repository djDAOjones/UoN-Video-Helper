# VH-24 — Survive real-world source properties

Working detail for the open backlog item. Measured 2026-08-25 across the 20
lecture sources in `samples/` (gitignored). All are H.264.

## Frame rate, and the one tool behind every anomaly

Eight files carry a frame-rate defect, and container metadata puts all eight in
the same family. The maintainer notes the corpus includes PowerPoint exports
from different people and systems; the correlation is total.

| Family | Signature | Files | Frame rates |
| --- | --- | --- | --- |
| **PowerPoint / Windows Media Foundation** | `mp42`/`mp41isom`, `handler_name=VideoHandler`, description `AVC Coding`, **no `encoder` tag** | 8 | **all 8 anomalous** |
| Adobe (MainConcept) | `Mainconcept Video Media Handler` | 6 | 25, clean |
| DaVinci Resolve | `Blackmagic Design DaVinci Resolve[ Studio]` | 4 | 25/30/50, clean |
| Sorenson Squeeze | `Sorenson Squeeze` | 1 | 25, clean |
| ffmpeg | `Lavf58.45.100` | 1 | 30, clean |
| Teams | `isom`/`isomiso2`, **no handler name at all** | 1 | 16 CFR |

PowerPoint's "Export to Video" runs at a nominal 30 fps but actually writes
**1000/33 = 30.303**. Frame interval measured over 900 frames is exactly 33 ms
with no spread — CFR on a millisecond grid, not VFR. On three of the eight it
then declares `30/1` in the header anyway:

| File | declared | actual |
| --- | --- | --- |
| `AMCS2007 MiaM` | 30/1 | 30.3028 |
| `LIBA3005 Created Spaces` | 30/1 | 30.3021 |
| `MLAC 3139 Module in a Minute` | 30/1 | 30.3030 |

Trusting the declared rate drifts ~1% — ~6 s over a 10 minute lecture, audible
desync, and exactly what acceptance criterion 6 exists to catch. `CULT2011` and
`CULT3033` declare 30303/1000 and mean it, so the odd rate is not itself the
defect; the disagreement is. The odd geometry below is the same family —
852×480 and 640×480 are PowerPoint export presets.

The signature is detectable, but the safer rule needs no detection: **always
measure the rate, never trust the header.** That covers PowerPoint, Teams and
whatever arrives next. Tool identification is worth keeping only for a
diagnostics panel, where "this looks like a PowerPoint export" helps someone
whose file behaves oddly.

## Audio

- **No audio track at all**: `Branded video graphics demo`, `River Evolution
  3-3`. Spec §5.4 treats this as a warning, not a failure. See VH-21.
- **Mono**: `CULT1027 Producing Film and Television` (1 channel).
- **PCM s16le, not AAC**: `AMCS3068 North American Film Adaptations` (`.mov`).
- **Mixed sample rates**: 44.1 kHz on nine files, 48 kHz on nine.

## Geometry

- `852×480` on three files — not 854, and awkward for chroma subsampling.
- `640×480` on one (4:3).
- `3840×2400` on `River Evolution 3-3` — **16:10**, not 16:9. Branding
  composited over this at a 16:9 aspect will letterbox or crop unless handled.
- Otherwise 1280×720, 1920×1080, 3840×2160.

## Frame rates present

25 (nine files), 30 (four), 30.303 (six), 50 (one — `LIBA2002`).

## Coverage gap

Durations run 1.4–13.8 min. Nothing approaches the 60 minute jobs spec §7.4
publishes limits for, and there is no true VFR file — the screen recordings
are CFR on an odd grid, which is a different defect from the VFR the conform
path was built for. Both gaps carry into VH-M2.

## Teams recording (added 2026-08-25)

`Meeting with Joe Bell (staff)-20260825_131504-Meeting Recording.mp4`, 212 MB,
**29.25 minutes** — the longest file in the corpus, which partly closes the
VH-M2 duration gap.

| Property | Value | Why it matters |
| --- | --- | --- |
| Frame rate | **16.000 fps**, declared `16/1` | §6.3 snaps to 24 → 50% duplicate frames |
| Frame interval | exactly 0.0625 s, zero variance at t=0/600/1200 s | **CFR, not VFR** |
| Timebase | 1/10000 | 100 µs grid, not the usual 1/90000 |
| Profile | Constrained Baseline, level 4.0 | no B-frames; real-time encoder |
| Video bitrate | 1.006 Mbps at 1920×1080 | already below our "smaller file" target |
| Audio | AAC-LC, **16 kHz**, **mono**, **3.9 kbps** | lowest rate in the corpus by 2.75× |

The headline: **Teams does not produce VFR.** It produces rock-solid CFR at a
low, non-standard rate — so the hazard the conform path was built against is
not the one that arrives. With the six 30.303 fps files, the real screen-
recorder pattern is *odd but stable* rates that no "nearest standard value"
rule handles well.

Its 1.006 Mbps video also means a "smaller file" re-encode at 1.5–2.5 Mbps
would make the file BIGGER. Needs a never-exceed-source guard.

## Meter validated at 16 kHz

The 16 kHz audio sits far below the 48 kHz the meter was validated at, so it
was checked against ffmpeg `ebur128` and matched to 0.02–0.03 LU. Recorded in
trajectory.md (2026-08-25); no action needed.
