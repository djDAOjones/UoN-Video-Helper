## Intent

Maintainer request, 2026-09-30: the steps "visually more separated", perhaps
as expanding and contracting sections that progress "when info was added" —
accessibility and UX paramount, suggestions invited. VH-91 did the separating.
This is the expanding and contracting, done where it is safe: between STAGES,
not between choices.

## Done when

See the backlog line.

## Where VH-91 left the page

Four numbered panels, always open once a video has been read:

1. Choose a video — the file, its own status line, what will not be carried
   over, Video properties
2. Closing branding
3. File size / quality
4. Create — the verdict, sound warnings, the button, the job's status line,
   progress, the result and Save

Trim (VH-96) lands as a step of its own and renumbers the rest;
`test/screen-text.test.ts` holds the numbers consecutive.

## Approach

The archived branch built it. On tag `archive/repository-review-implementation`:
`src/ui/workflow.ts` (a pure `workflowStepState`), `workflow.test.ts`, the
`.workflow-*` rules in `app.css`, and `showWorkflowStage` and
`focusNextWorkflowControl` in `main.ts`.

- Four stages — choose, review, create, save. One body open at a time; a
  finished stage shows a one-line summary; `aria-current="step"` marks the
  open one.
- It advances on three things only: a video is read, Create is pressed, the
  job finishes. None of them is a changed control.
- What a port adds to the archive: the option panels stay separate INSIDE
  the set-up stage; a folded stage can be reopened; nothing folds while it
  shows an error.
- It is a port, not a merge. The archive's `main.ts` was built on authority
  modules HEAD does not have, and it moves `#process-actions` between stage
  bodies, which VH-36 would want re-examined.
- There are two status lines now, one per step (VH-91). A folded stage must
  not take a live region with it: whichever is speaking has to stay on the
  page.

### Rejected — advancing when a choice changes

A `<select>` or radio group changes value on every arrow key. Advancing on
change would shut the section under a keyboard user on their first keypress,
before they had reached the option they wanted — a change of context on
input (WCAG 3.2.2), failing silently for exactly the users the AAA target is
for. And because every step holds a default, there is no moment at which
information "arrives" to advance on.

## Constraints

- Carbon productive, in project code. Native `<details>` wherever a
  disclosure is wanted.
- The verdict depends on the preset and, later, the trim, so it re-renders
  when either changes. It must not take focus when it does.
- `prefers-reduced-motion` for any fold.
