# VH-34 — The composite may still be engine-dependent

Raised by an external code review 2026-08-25 and verified against the source
the same day. Not yet measured in a browser — that measurement IS this ticket.

## The claim

`composite.ts`'s header argues that canvas `drawImage` cannot be trusted for
the blend, because the engines disagree about whether a decoded frame's colour
is premultiplied — Chrome and Safari return 202 compositing the white onset
over white, Firefox returns 255. So the blend was moved to the CPU.

But `compose()` still routes the branding frame **through a canvas** to get at
its pixels (`composite.ts:135`):

```
brand.draw(this.overlayContext, fit.x, fit.y, fit.width, fit.height)
const over = this.overlayContext.getImageData(0, 0, width, height)
compositePremultiplied(under.data, over.data)
```

`getImageData` returns **straight** (un-premultiplied) RGBA by specification.
So the same engine disagreement plausibly reappears one step later, at the
readback rather than at the blend:

| Engine treats the decoded frame as | Canvas holds | `getImageData` returns | `compositePremultiplied` receives |
| --- | --- | --- | --- |
| straight (Chrome, Safari) | RGB 75, α 75 | **(75, 75)** | correct — matches the master |
| premultiplied (Firefox) | un-premultiplied to RGB 255 | **(255, 75)** | wrong — 3.4× too bright |

If that is what happens, `out = brand + source × (1 − a)` becomes
`255 + source × 0.71` in Firefox: a blown white fringe wherever the build sits
over dark picture.

## Why it has not been seen

- **Both compositing modes are opt-in and off by default.** `hard-cut` is the
  default and composites nothing, so no default job touches this path.
- **Over white the error is invisible**, and white is what `spike/alpha.ts`
  measures. The existing Firefox verification tested `drawImage` over white —
  not `compose()`'s readback.
- `composite.test.ts` tests `compositePremultiplied` as a pure function with
  synthetic premultiplied input, which is correct and proves nothing about
  what the canvas hands it.
- `spike/modes.ts` checks output durations, not pixels.

So nothing in the repo currently exercises the failure.

## The measurement that settles it

In `spike-alpha.html`, draw the **white** onset onto a cleared transparent
canvas and print the `getImageData` RGBA at a pixel inside the ramp:

- **(75, 75, 75, 75) in all three engines** → the design holds, the CPU blend
  is genuinely portable, and this ticket closes as a recorded verification
  plus a regression test.
- **(255, 255, 255, 75) in Firefox** → `over-picture` and `over-freeze` are
  wrong in Firefox, and the fix is to detect the engine's convention once at
  startup and re-premultiply on readback where needed.

Do the blue onset too. Blue is the default colour and its RGB is not at the
white ceiling, so the two carry different error magnitudes and only one of
them is what a real user would see.

## The claim that outruns the evidence

Whatever the answer, `public/branding/README.md:30` currently reads that all
three closing modes "work in every supported browser", and `trajectory.md`
says the same. That was concluded from a `drawImage`-over-white measurement,
which does not cover this path. Either the measurement above extends the claim
honestly, or the claim is narrowed to what was actually tested.
